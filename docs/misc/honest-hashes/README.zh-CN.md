附件是 18 行长字符串，长得就像 SHA-256。题目叫「诚实的哈希」——哈希本身没撒谎，秘密也不在哈希里。它在字符的码点上。

明确将西里尔 `а/с/е` 映射为拉丁 `a/c/e` 后，第 1 行和第 12 行得到相同摘要，等于 `123456` 的 SHA-256。可见哈希相同，字符码点却可携带不同的信息。

差别在 Unicode 上：拉丁小写 `a`、`c`、`e` 是 U+0061 / U+0063 / U+0065；西里尔 `а`、`с`、`е` 是 U+0430 / U+0441 / U+0435。渲染出来几乎一样，码位不同。

第 1 行前六个取样字符为 `e е e с a c`，码点依次为 `U+0065 U+0435 U+0065 U+0441 U+0061 U+0063`，对应位 `010100`。显式外形映射将第 1、12 行都转换成：

```text
8d969eef6ecad3c29a3a629280e686cf0c3f5d5a86aff3ca12020c923adc6c92
```

## 每个字母是一位

这三种字母各有两种形态，正好构成一个二进制通道：

- 拉丁形态记 0
- 西里尔形态记 1

其余字符（数字、其他字母）不参与取样。按文件顺序扫一遍，把每个命中的字母换成一位：

```python
mapping = {'a':'0','c':'0','e':'0','а':'1','с':'1','е':'1'}
bits = ''.join(mapping[c] for c in text if c in mapping)
```

一共 240 位，按 MSB 优先每 8 位组一个字节，得到 30 字节：24 字节的 flag 加 6 个零字节。

```text
RBH{n0t_3v3ry_a_1s_an_a}
```

flag 说的就是这题本身：不是每个 a 都是 a。

## 两件别做错的事

**别说 NFKC 会自动转换。** Unicode 规范化不会把西里尔 `а` 变成拉丁 `a`——这是显式映射，靠的是查表，不是归一化。写错了方法，结论就站不住。

**别先覆盖原文本再分析。** 任何将西里尔字母替换成拉丁外形的操作都会破坏隐藏位，应保留原始 UTF-8 字节。分析必须在原始字节上做。

## 怎么确认方向没搞反

240 能整除 8、解出来的前缀是 `RBH{`、整串可读——三条一起才算证据。把 0/1 反过来读、或者改成 LSB 优先，得到的都是乱码。

脚本会原样打印解出的 bytes（保留末尾填充），最后只去掉 NUL。复杂度 O(n)。

顺带一提：这些串看起来是普通 SHA-256，但恢复隐藏消息**不需要破解任何哈希**。哈希只是载体。
