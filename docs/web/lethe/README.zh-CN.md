Lethe 是遗忘之河。这题要区分**记忆行**和**回声**：记忆被删后，回声仍可能保留。以下 HTTP 现象来自组织方官方题解；本地示例只复现数据库机制，不连接赛事服务。

## 1. 分别检查记忆与回声

`/memory/N` 对自己的记录返回 200，对其他人的现存记录返回 403，对不存在的记录返回 404。`/resonance/N` 则独立表明该编号是否还留有回声。

| 编号 | 记忆状态 | 含义 |
|---|---|---|
| 1、2、4、5、6 | 封存，403 | 存在但当前会话无权删除 |
| 3、9 | 记忆不存在，404；回声存在 | 记忆删除后留下的孤立回声 |
| 10、11、12 | 自己的记录，200 | 当前会话可删除的记录 |

第二个接口使 9 成为有依据的目标。仅有编号空洞不能证明那里曾有记录；记忆消失而回声仍在，才是关键证据。

## 2. 判断哪个编号能重新取得

普通 SQLite `INTEGER PRIMARY KEY` 在插入时省略编号，通常分配**当前最大 rowid 加一**，并不会优先填最小空洞。`AUTOINCREMENT` 有不同的防复用规则，本题不按那个模型解释。

10–12 存在时，新建得到 13。删除最高的 13 再建，仍得到 13。进一步删除自己拥有的全部高位记录，剩余最大编号就是 6，连续新建三次便得到 7、8、9。

为什么不取回 3？封存的 6 无权删除，它构成分配器无法越过的下限。两个孤立回声中，9 可以通过当前操作取得，3 不行。

## 3. 重建 9，读取继承的回声

官方给出的路由与操作顺序如下。这是赛事期间请求的说明，离线脚本不发送这些请求：

```text
GET  /memory/N 和 /resonance/N   比较记忆与回声是否存在
POST /forget/10                 删除自己的高位记录
POST /forget/11                 删除自己的高位记录
POST /forget/12                 此时剩余最大编号为 6
POST /remember                  新记忆编号 7
POST /remember                  新记忆编号 8
POST /remember                  新记忆编号 9
GET  /memory/9                  读取新记忆及继承的回声
```

如果前面试建了 13，也要先删除它，再连续新建三次。新记录的标题和正文并不重要。旧回声只按整数 9 关联，新建的 9 因此接到了已删除记录的回声。回声直接包含带后缀的完整 flag：

```text
RBH{th3_r1v3r_f0rg3ts_th3_row_n0t_th3_numb3r_9_b0a6}
```

`b0a6` 是读出的正文的一部分，无需猜测它的哈希生成公式。

## 4. 在本地复现身份关联错误

```powershell
python src/solvers/lethe/mechanism_demo.py
```

[内存 SQLite 示例](../../../src/solvers/lethe/mechanism_demo.py) 使用合成的 `DEMO_ONLY` 回声，验证删除自己的高位记录后得到 `[7, 8, 9]`、新 9 继承旧回声，以及启用外键并级联删除后旧关联消失。同时验证反例：6 仍存在时，空着的 3 不会优先分配。

根因是关联对象的生命周期不同步。关联应使用稳定身份，启用外键约束并同步删除，同时检查关联对象的访问权限。一个可能复用的整数不能充当历史身份凭据。本地示例验证这种机制，赛事 HTTP 现象仍以官方文章为来源。
